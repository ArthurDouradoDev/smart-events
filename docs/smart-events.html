01Visão geral

Smart Events é um sistema de monitoramento de rede móvel (telecom) usado durante eventos — partidas, shows, comícios — em que é crítico acompanhar, em tempo real, a saúde das células de rede da área e a qualidade de sinal de pessoas específicas (VIPs).

O sistema responde a duas perguntas operacionais simultâneas:

  • A rede está aguentando? — utilização de PRB, tráfego, throughput, acessibilidade e número de usuários por célula/site, plotados num mapa e em gráficos.
  • Os VIPs estão com bom sinal? — RSRP/RSRQ e célula servidora de cada VIP rastreado, com indicação se estão ou não dentro da área do evento.

Arquitetura em dois tiers

O projeto se divide em duas aplicações que compartilham os mesmos arquivos de configuração:

App desktop (operador)

Janela PyWebView (HTML/CSS/JS + backend Python). Coleta dados do iManager, persiste em SQLite local e exibe mapa, gráficos, painel de VIPs e alertas em tempo real. Cada operador roda a sua instância.

Servidor central (config)

Servidor FastAPI que funciona como fonte única de verdade para configuração: cadastro de eventos e de VIPs. Inclui uma UI web de autoria (upload de planilha de sites, desenho do polígono, CRUD de VIPs).

Pontos importantes da divisão de responsabilidades:

  • Configuração (eventos, VIPs, limiares, polígono) é sincronizada via servidor central — todos os operadores enxergam a mesma definição.
  • Medições ao vivo (KPI das células, RSRP/RSRQ dos VIPs) ficam locais em cada instância — não há cross-sync em tempo real desses dados.

02Como executar

O ponto de entrada é main.py. Os modos de execução são selecionados por flags de linha de comando:

ComandoDescrição
python main.pyProdução. Coleta dados reais do iManager (requer VPN do cliente conectada).
python main.py --mockDesenvolvimento com MockCollector — dados sintéticos, sem dependências externas.
python main.py --devAbre o DevTools na janela e eleva o log para DEBUG.
python main.py --serveSobe apenas o servidor FastAPI (sem janela), em 0.0.0.0:8000.
python main.py --get-sessionSubprocesso de renovação de sessão (Playwright). Chamado internamente pela coleta — ver seção 12.

Flags combináveis, ex.: python main.py --mock --dev.

Dependências (requirements.txt)

pywebview>=4.4.1   # GUI desktop
requests>=2.31.0   # cliente HTTP (coleta + sync)
schedule>=1.2.1    # (presente; o scheduler usa threading)
watchdog>=3.0.0    # monitoramento da pasta de CSV (fase 1)
playwright>=1.40.0 # automação de navegador (renovação de sessão)
fastapi>=0.100.0   # servidor central
uvicorn>=0.22.0    # runner ASGI

Fluxo de inicialização (main.py)

  1. Garante stdout/stderr válidos em UTF-8 (importante no .exe sem console) e configura logging.
  2. Instala o buffer de logs em memória (core/log_buffer.install()) — alimenta o painel </> do frontend.
  3. No Windows, cria um Job Object com KILL_ON_JOB_CLOSE para que subprocessos do Playwright (e seus Chromium) sejam encerrados junto com o app — evita órfãos e o popup "Failed to remove temporary directory _MEI…".
  4. Inicializa o banco SQLite (global + por evento).
  5. Sobe o servidor FastAPI embarcado em uma thread daemon (127.0.0.1:<porta>) e injeta a URL na Api._server_url.
  6. Cria a janela PyWebView (1440×900, fundo #0D1117) apontando para frontend/index.html e expõe a instância de Api.
NotaO modo privado do webview fica desabilitado de propósito, para preservar cookies/perfil de sessão entre execuções.

05A ponte Frontend ↔ Backend

O frontend não fala HTTP com o backend Python: ele chama métodos Python diretamente através da ponte do PyWebView, window.pywebview.api. O wrapper fica em frontend/js/bridge.js.

Como a ponte funciona

  • bridge.js expõe o objeto API com métodos em camelCase que delegam para os métodos Python (snake_case) de api/api.py.
  • As chamadas que chegam antes de o PyWebView estar pronto são enfileiradas e despachadas no evento pywebviewready.
  • Se o PyWebView não responder em ~1s (ex.: abrir o index.html direto no navegador), o bridge entra em modo mock e devolve dados sintéticos — permite desenvolver o frontend isolado.
  • Todo método retorna uma Promise.

Contrato de retorno

Por convenção do projeto (ver CLAUDE.md), métodos da Api nunca lançam exceção: capturam o erro e retornam {"ok": false, "error": str}. Sucesso retorna {"ok": true, ...} ou diretamente uma list.

// frontend/js/bridge.js (forma)
const API = {
  async call(method, ...args){ /* enfileira ou chama window.pywebview.api[method] */ },
  getActiveEvent(){ return this.call('get_active_event'); },
  getSites(eventId, ts, metric){ return this.call('get_sites', eventId, ts, metric); },
  getKpiSeries(eventId, siteId, metric, minutes, cellId){ ... },
  ...
};

Gráficos "por célula" e regras de agregação

Ao selecionar um site, o seletor de célula oferece três modos, resolvidos em get_kpi_series:

  • __all__ — uma linha colorida por célula (campo cells_data).
  • __media__ — uma linha única com a média das células.
  • célula específica — uma linha só daquela célula.

A agregação de múltiplas células num único valor por timestamp (gráfico) depende da métrica:

MétricaAgregação no gráfico
throughput_dl / throughput_ulsoma (capacidade do site)
availability / accessibilitymédia
rsrp / rsrqmédia
utilization, user_count (demais)máximo (pior caso)
AtençãoA agregação para a coluna da lista de sites (_aggregate_metric_for_list) usa regras ligeiramente diferentes: volume (user_count, traffic_volume_*) vira share % da soma; accessibility usa mínimo; rsrp/rsrq/throughput usam média; utilização usa máximo. São contextos distintos (gráfico vs. lista).

09Servidor central (FastAPI)

Em server.py. Existe para dar uma fonte única de verdade de configuração a múltiplos operadores na rede: todos veem o mesmo polígono, lista de sites, limiares e VIPs. Roda em 0.0.0.0:8000 (acessível pela rede local) e também é subido embarcado pelo app.

Detecta o IP local no startup, habilita CORS para qualquer origem e é ciente de PyInstaller: separa RESOURCE_DIR (recursos read-only do bundle) de DATA_DIR (gravável, ao lado do .exe), garantindo que app e servidor compartilhem o mesmo server_data/. Na primeira execução, semeia server_data/ a partir da cópia embutida.

10UI de autoria (server_frontend)

SPA com abas Eventos e VIPs, tema escuro, mapa Leaflet servido de /static/. É aqui que os eventos são criados — algo que não existe no app desktop (que apenas carrega e ativa).

Aba Eventos

Lista: cards com nome, id/slug, badge de status, datas, nº de sites e PM Task ID, com botões editar/excluir e "Novo Evento".

Formulário:

  • Geral — nome, id/slug (auto a partir do nome), status, início/fim.
  • Planilha de sites — zona de drag-and-drop que envia o arquivo a /api/parse-sites e mostra "Carregados X sites com Y células".
  • OSS / Coleta — região (SP/RJ), pasta de import CSV, base URL da API.
  • iManager — PM Task ID (opcional).
  • Limiares — RSRP/RSRQ warning/critical, utilização warning/critical, disponibilidade crítica.
  • Mapa — sites plotados como setores; ferramentas de polígono.

Desenho do polígono

  • Auto — calcula o bounding box dos sites e aplica um padding (slider 100–2500 m), gerando um polígono retangular ao redor da área.
  • Manual — clique no mapa para adicionar vértices; suporta formas irregulares.

Ao salvar, POST /api/events com o payload completo. Em modo edição, se o id mudou, apaga o id antigo antes de gravar o novo.

Aba VIPs

CRUD de VIPs: nome, id/slug, função (role), OSS (SP/RJ), Task ID (para o Signaling Trace) e notas. Salva via POST /api/vips.

Parsing de planilha (/api/parse-sites)

Endpoint robusto baseado em pandas:

  • Aceita .xlsx/.xls (via read_excel) e CSV/TSV/TXT com separador autodetectado (, ; \t) e múltiplas codificações (UTF-8, Latin-1, UTF-16, CP1252).
  • Mapeamento flexível de colunas (case-insensitive), ex.: lat/latitude/coordenada y, lng/lon/longitude, enodebid/site_id/codigo site, cellid/celula, nename/sitename/estacao, cellname, azimuth/azimute/direcao.
  • Colunas obrigatórias: enodebid, cellid, nename, cellname, longitude, latitude, azimuth — ausências retornam 400.
  • Agrupa células por site (enodebid), pula linhas sem coordenada, deduplica células e devolve a hierarquia normalizada com beamwidth padrão de 120°.

11Fluxos de coleta (iManager)

A coleta está em core/collector.py, em duas fases:

  • Fase 1 (CSV) — CsvCollector monitora a pasta oss.import_folder e processa exports CSV do iManager.
  • Fase 2 (HTTP, implementada) — HttpCollector consulta o iManager diretamente via sessão autenticada, renovando a sessão via Playwright quando expira.

build_collector(event_config, mock) escolhe a implementação: mock=True → MockCollector; integration.collection_type="csv" → CsvCollector; senão HttpCollector.

base_url regional

Precedência (mesma usada por check_vpn e reauth_session): oss.base_url explícito → mapa regional → fallback SP.

_REGIONAL_BASE_URLS = {
  "SP": "https://10.220.50.9:31943",
  "RJ": "https://10.220.30.9:31943",
}
_DEFAULT_BASE_URL = "https://10.220.50.9:31943"  # fallback = SP

Ciclo KPI (módulo Monitoring/PM)

scheduler._collect_kpis()  (thread, intervalo ~120s)
   │
   ├─► HttpCollector.collect_kpis()
   │     ├─ carrega sessão "monitoring" (cookies + roarand de session.json)
   │     ├─ POST /rest/oss/access/pm/v1/monitor/task/result
   │     │     (taskId = integration.pm_task_id OU task da sessão)
   │     ├─ DESCOBERTA DINÂMICA: 1º ciclo consulta objNoExecTimes vazio p/ obter
   │     │     todos os objNo; mapeia objNo → {cell_id, site_id} e cacheia
   │     ├─ parse/flatten do JSON (counterRes {name,value})
   │     │     + escala de contadores RJ (bits→MB, kbps→Mbps)
   │     └─ retorna [{site_id, cell_id, event_id, timestamp, metric, value}, ...]
   │
   ├─► db.insert_kpi_batch(...)            (banco POR EVENTO)
   └─► scheduler._evaluate_kpi_alerts(...) (compara limiares → insert_alert)

Erros de conexão (timeout/ConnectionError) geram alerta "VPN"; SessionExpiredError dispara a renovação (seção 12).

Ciclo VIP (módulo Trace/FARS)

Cada VIP tem uma task_id de Signaling Trace. Para cada uma, um workflow de 4 passos:

scheduler._collect_vips(mode)   express (~60s) | full (~600s)
   │
   └─► para cada task_id de VIP:
        1. GET  .../fars/v1/traceresult/pre-check?taskId=…   (inicia sessão de trace)
        2. GET  .../fars/v1/traceresult/query/result?taskId=…  (obtém sess_msg_id)
        3. POST .../fars/v1/traceresult/query/filter-by-cols    (msgs RRC_MEAS_RPRT,
              { colFilterDto: Message Type = RRC_MEAS_RPRT,        ordem cronológica
                pageDto: {isAscend:false, pageSize:1000, taskId, msgId} }   reversa)
        4. POST .../fars/v1/message/explain-info                 (decodifica RSRP/RSRQ
                                                                   do conteúdo bruto)
        → [{vip_name, event_id, timestamp, serving_cell, rsrp, rsrq, in_event}, ...]

Decodificação de sinal a partir do conteúdo da mensagem:

rsrpResult: 0x30 (48)  →  RSRP = 48 - 140   = -92 dBm
rsrqResult: 0x3A (58)  →  RSRQ = 58/2 - 19.5 = -10.5 dB

Célula servidora: extraída da mensagem; match case-insensitive; IDs globais decodificáveis (4G ECI // 256, 5G NCI // 4096).

Importante (lição do RJ)O módulo FARS aceita uma sessão de trace ativa por token: a coleta de VIPs roda serializada (_VIP_MAX_WORKERS = 1), pois paralelizar invalidava os sess_msg_id. Ver seção 15.

Matching célula → evento (4 estratégias)

BaseCollector._cell_in_event() aceita: (1) match exato com células do evento; (2) obj_no mapeado; (3) substring/prefixo de site id/nome; (4) decodificação de ECI/NCI.

12Sessão, SSO/CAPTCHA & renovação

O iManager exige login autenticado. A automação fica em core/session_renew.py (Playwright), e os tokens vão para data/session.json.

session.json

Guarda, por módulo, os cookies e o token CSRF (roarand). Os módulos monitoring (KPI) e trace (VIP) compartilham o cookie jar, mas têm roarand próprios.

{
  "monitoring": { "cookies": [...], "roarand": "…", "task_id": 374 },
  "trace":      { "cookies": [...], "roarand": "…", "task_id": 123 }
}

Detecção de expiração

A sessão é considerada inválida quando:

  1. HTTP 401/403;
  2. A URL da resposta redireciona para SSO/login (unisso ou login.action);
  3. O HTML contém marcadores de login/sso/authentication.
Convenção do projetoAs sondas de sessão devem inspecionar a URL da resposta para detectar redirecionamento SSO — a página de login pode retornar HTTP 200 com HTML longo, o que inviabiliza a busca por palavras-chave só nos primeiros 2000 caracteres do corpo.

Renovação automática (headless)

coleta detecta SessionExpiredError
   │
   ├─ checa backoff (60s → 120s → 180s → 300s, exponencial, por módulo)
   ├─ single-flight: um lock evita renovações concorrentes (monitoring + trace)
   └─ subprocess:  python main.py --get-session   (Playwright headless)
         exit 0  (EXIT_SUCCESS)          → recarrega session.json, zera backoff
         exit 2  (EXIT_NEEDS_INTERACTIVE)→ CAPTCHA/SSO: marca módulo, emite alerta,
                                            auto-abre navegador visível (single-flight)
         exit 1  (EXIT_GENERIC_FAIL)     → aplica backoff e tenta depois

Reauth interativo (CAPTCHA/SSO)

Quando o login exige CAPTCHA, o headless não resolve. O botão "Reautenticar" (drawer de alertas / modal de sync) chama Api.reauth_session() → HttpCollector.run_interactive_reauth(), que abre um navegador visível para o operador concluir o login. Ao terminar, a coleta detecta a mudança do roarand e retoma. Após uma tentativa manual há um cooldown (~5 min).

Credenciais por região

Resolução: data/credentials.json[REGIÃO] → mapa interno por região → conta padrão (SP) → entrada manual para regiões não configuradas.

13Sync app ↔ servidor

A sincronização cobre apenas configuração. As medições ao vivo nunca trafegam pelo servidor.

STARTUP / save_settings
   app ──GET /api/events──► servidor      → db.sync_events_from_server()
                                            (upsert em events + sites por evento)

CARREGAR EVENTO (load_event)
   app ──POST /api/events──► servidor     → db.export_event_to_server(config)
                                            (distribui o evento às outras instâncias)

ATIVAR EVENTO (activate_event)
   detecta oss.region do evento
   app ──GET /api/vips?oss=RJ──► servidor → db.sync_vips_from_server(oss)
                                            (upsert em vips + cria event_vips)
   scheduler.start(config) → começa a coletar KPI/VIP

ISOLAMENTO
   kpi_measurements / vip_measurements  →  ficam LOCAIS (SQLite da instância)
   eventos / vips / limiares / polígono →  SINCRONIZADOS via servidor

O CRUD de VIPs no app (create/update/delete_vip) e as associações (assign/unassign_vip_to_event) também re-exportam para o servidor, mantendo as instâncias consistentes.

14VPN, diagnóstico & logs

Checagem de VPN

Api.check_vpn() resolve o host do OSS (precedência oss.base_url → regional → SP) e roda o ping nativo do Windows (ping -n 2 <host>, sem janela). Conectado = presença de TTL= na saída. O frontend repete a cada 15 min e mostra o #vpn-modal quando cai.

Buffer de logs (painel </>)

core/log_buffer.py instala um handler de logging que mantém um ring buffer em memória (~3000 entradas) capturando collector, scheduler e renovação. O drawer de logs lê via get_collection_logs(), e há clear_collection_logs() e download_collection_logs() (salva .log em Downloads).

Status de coleta

scheduler.get_status() (exposto por get_collection_status()) devolve, por módulo KPI/VIP: estado (idle|running|ok|error), último sucesso, contagem, e — para VIP — o modo (express|full). A seção de sessão informa needs_interactive e a região.

15Limitações conhecidas & lições

Resumo de relatorio-erro-404.md — diagnóstico de erros 404 na coleta da região RJ (SP funcionava). Endpoints afetados: /rest/oss/access/pm/v1/monitor/task/result (KPI) e o filter-by-cols do FARS (VIP).

Resolvido — concorrência de VIPO FARS permite só uma sessão de trace ativa por token; requisições paralelas a vários VIPs invalidavam os sess_msg_id. Fix: _VIP_MAX_WORKERS = 1 (coleta serializada).
Resolvido — query string em POSTO proxy/WAF da RJ rejeitava POST com query string ?nocache= (GET passava). Fix: remoção do ?nocache= dos POSTs.
Em abertoHipóteses remanescentes: task IDs inválidos (deletados ou de outro usuário); diferença de versão de API entre regionais; drop do header roarand/cookie ao passar pela VPN; degradação de sessão entre requisições.
